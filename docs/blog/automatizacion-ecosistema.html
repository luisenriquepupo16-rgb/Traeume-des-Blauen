Cómo automaticé mi ecosistema de desarrollo con GitHub Actions y Discord

Durante los últimos meses he construido, poco a poco, un ecosistema de automatización alrededor de mi proyecto. GitHub Actions corre workflows que hacen cosas sin que yo tenga que hacerlas. Discord recibe notificaciones. Los Gists almacenan estado. Y todo se comunica entre sí sin intervención manual. Este es un repaso de cómo funciona.

El punto de partida

Al principio, todo era manual. Cuando terminaba un build, iba a GitHub a ver si había fallado. Cuando quería saber cuántas descargas tenía una app, entraba al panel de releases. Cuando quería publicar una nueva versión, ejecutaba un script en PowerShell.

Era sostenible cuando tenía 1 proyecto. Insostenible cuando tenía 5. Y ya estaba empezando a perder cosas por el camino: releases sin hacer, builds sin revisar, versiones desincronizadas.

La idea: GitHub Actions como centro de operaciones

La solución fue usar GitHub Actions como el centro de todo. Todos los repositorios tienen workflows que se disparan en momentos específicos (push, cron, workflow_dispatch) y hacen cosas concretas. La comunicación con el exterior se hace a través de webhooks de Discord y de un Gist central que actúa como almacén de estado compartido.

El Gist es clave. Es un archivo JSON público (o privado, según cómo lo configures) que todos los workflows leen y escriben. Sirve como "memoria compartida" entre workflows que no se conocen entre sí.

Los workflows que tengo

1. Release and Catalog

Cuando hay cambios en apps/, este workflow:

  • Detecta qué app ha cambiado.
  • Crea (o recrea) el release de GitHub con el APK y el icono.
  • Ejecuta un script PowerShell que regenera catalog.json.
  • Hace commit del JSON actualizado con [skip ci] para no dispararse a sí mismo.

Es el workflow más importante del proyecto. Sin él, la app no sabría qué apps existen.

2. Download Notifier

Corre cada 15 minutos. Consulta las estadísticas de descargas de todos los releases, las compara con el estado anterior (guardado en el Gist), y si hay descargas nuevas, notifica a Discord. También guarda un histórico diario para tener estadísticas a largo plazo.

3. Version Checker

Corre cada día a las 6 AM UTC. Compara la versión declarada en cada info.md con la versión del último release publicado. Si no coinciden, avisa a Discord. Así sé si me he olvidado de crear un release.

4. Issue Responder

Cuando alguien abre un issue en el repositorio, este workflow:

  • Etiqueta el issue según su contenido (bug, sugerencia, encargo, triage).
  • Responde automáticamente con un mensaje apropiado.
  • Notifica a Discord.

Además, un job programado cierra issues inactivos después de 30 días, con un aviso previo.

5. Dev Diary

Cada día a las 6 PM (hora de Cuba), este workflow recopila la actividad del día en varios repositorios: commits, releases, issues. Si hubo movimiento, envía un resumen a Discord. Si no, envía un mensaje gracioso del tipo "hoy no hubo movimiento, supongo que descansaste".

6. Repo Thermometer

Cada domingo, calcula un "termómetro" de actividad semanal: cuántos commits, releases e issues hubo en todos los repositorios. Lo clasifica (semana muerta, tranquila, normal, muy movida) y lo envía a Discord.

7. Workflow Failure Alert

Escucha a los otros workflows. Si alguno falla, notifica a Discord con un enlace al log. Así me entero de los problemas sin tener que ir a GitHub a revisar.

8. Gemini Chat

Es el workflow del chatbot. Cuando un cliente (la web, la app, o un bot de Discord) envía una pregunta, este workflow:

  • Carga el catálogo de apps.
  • Construye un prompt con el catálogo como contexto + el historial de la conversación.
  • Llama a Gemini con reintentos automáticos.
  • Envía la respuesta a Discord o la guarda en el Gist (según el cliente).

La comunicación con Discord

Discord actúa como mi "panel de control". Recibo notificaciones de:

  • Descargas nuevas de mis apps.
  • Releases publicados.
  • Issues abiertos.
  • Workflows fallidos.
  • Resúmenes diarios y semanales.
  • Respuestas del chatbot.

Todo llega a un canal privado que solo yo veo. Es como tener un asistente que me avisa de todo lo que pasa sin que yo tenga que revisar nada.

Lo que aprendí

Tres lecciones:

  1. El Gist como memoria compartida es muy potente. Permite que workflows independientes se comuniquen sin necesidad de un backend real. Es una solución simple y gratuita.
  2. Automatizar la comunicación es tan importante como automatizar las tareas. De nada sirve que un workflow se ejecute si tú no te enteras de que ha pasado. Las notificaciones son lo que cierra el ciclo.
  3. Empezar pequeño y crecer. No empecé con 8 workflows. Empecé con 1 (release-and-catalog). Luego añadí 2. Luego 3. Cada uno resolvía un problema concreto. No intenté hacerlo todo a la vez.

Conclusión

Este ecosistema me ha ahorrado horas y horas de trabajo manual. Lo que antes era "revisar GitHub todos los días" ahora es "recibir notificaciones en Discord". Lo que antes era "actualizar un JSON a mano" ahora es "hacer push y olvidarse".

Si estás empezando con GitHub Actions, mi recomendación es: automatiza primero las cosas que haces todos los días. Luego las que haces cada semana. Luego las que haces cada mes. No intentes automatizar todo el primer día.
