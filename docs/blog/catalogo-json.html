Cómo estructuré el catálogo de apps con un JSON generado automáticamente

Una de las decisiones que más tiempo me ahorró en Träume des Blauen fue automatizar la generación del catálogo. En vez de mantener a mano una lista de aplicaciones, el catálogo se genera solo a partir de la estructura de carpetas. Este es el proceso.

El problema

Cuando empecé, tenía varias apps publicadas. Cada vez que añadía una nueva, tenía que:

  • Actualizar la web con los datos de la app.
  • Actualizar la app Android con los mismos datos.
  • Mantener todo sincronizado.

Era tedioso y propenso a errores. Se me olvidaba actualizar un lado u otro, y los datos quedaban inconsistentes.

La idea

La solución fue simple: separar los datos de la presentación. Los datos viven en un archivo JSON generado automáticamente. La presentación (web, app Android) solo lee ese JSON. Así, solo hay que mantener los datos en un sitio, y todo lo demás se actualiza solo.

La estructura de carpetas

Cada app vive en su propia carpeta dentro de apps/:

apps/
├── converty/
│   ├── converty_v1.2.0.apk
│   ├── icon.png
│   └── info.md
├── magic_world/
│   ├── magic_world_v2.1.10.apk
│   ├── icon.png
│   └── info.md
└── ...

El archivo info.md contiene los metadatos de la app en formato YAML (frontmatter) + cuerpo markdown. Por ejemplo:

---
name: Converty
version: 1.2.0
version_code: 5
package: com.converty.neki
category: Utilidades
technologies:
  - Kotlin
  - Apache POI
---

## Description

Aplicación Android que convierte documentos...

El workflow

En GitHub, un workflow detecta cambios en la carpeta apps/ y hace dos cosas:

  1. Crea un release de GitHub con el APK y el icono.
  2. Ejecuta un script que recorre todas las apps, lee su info.md, y genera el catalog.json.

El script está escrito en PowerShell. Por cada app:

  • Lee el frontmatter YAML.
  • Busca el APK y el icono.
  • Calcula el hash SHA-256 del APK.
  • Construye una entrada del JSON con URLs apuntando al release.

El JSON resultante

El catalog.json tiene esta estructura:

{
  "version": 1,
  "generated_at": "2026-10-11T...",
  "site": {
    "title": "Traeume des Blauen",
    "author": "Dreamer"
  },
  "apps": [
    {
      "id": "converty",
      "name": "Converty",
      "version": "1.2.0",
      "category": "Utilidades",
      "icon": "https://...",
      "apk": {
        "url": "https://...",
        "size_bytes": 19626720,
        "sha256": "..."
      }
    }
  ]
}

Cada app tiene toda la información necesaria para ser mostrada y descargada.

Los consumidores

Dos cosas leen ese JSON:

  • La web del portafolio, que lo lee desde JavaScript y renderiza las tarjetas.
  • La app Android, que lo descarga con Ktor y lo cachea con DataStore.

Ambos leen la misma URL: https://luisenriquepupo16-rgb.github.io/Traeume-des-Blauen/catalog.json. Cuando el catálogo cambia, ambos se actualizan solos.

Los detalles importantes

Encabezados sin tildes

Un detalle que me costó descubrir: los encabezados del cuerpo del info.md (## Description, ## Uso) tienen que estar en inglés y sin tildes. La razón es que PowerShell 5.1 puede corromper las tildes al leer el archivo, y el parser deja de encontrar los encabezados. El contenido sí puede estar en español.

Nombres de archivos sin caracteres especiales

Los APKs deben nombrarse como <app-id>_v<version>.apk, sin diéresis, sin mayúsculas. Los iconos siempre icon.png. Esto evita problemas de encoding en distintos sistemas.

El workflow hace commit del JSON

Después de generar el catalog.json, el workflow hace commit automático con un mensaje que incluye [skip ci]. Así no se dispara a sí mismo en bucle.

Lo que aprendí

Tres lecciones:

  1. Separar datos de presentación es clave. Cuando los datos viven en un sitio y la presentación en otro, todo se actualiza solo. No hay que sincronizar nada a mano.
  2. La automatización paga a largo plazo. Invertir 2 horas en configurar un workflow ahorra decenas de horas de mantenimiento manual.
  3. Los detalles técnicos importan. El encoding, los nombres de archivos, los encabezados sin tildes... Son detalles pequeños que, si se ignoran, rompen todo el sistema.

Conclusión

Automatizar el catálogo fue una de las mejores decisiones del proyecto. Ahora añadir una app nueva es tan simple como crear una carpeta con tres archivos y hacer push. El resto se hace solo.

Si estás manteniendo un catálogo a mano, mi recomendación es: automatízalo. No tiene que ser perfecto, solo tiene que quitar el trabajo manual del medio.
